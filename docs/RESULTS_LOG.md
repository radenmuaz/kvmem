- **`hmn_stitch_src1024.py` — REDESIGNED, multi-hop relay-chain version abandoned before completing a full run.** Original attempt: src=1024 (`chunk_len=64, n_chunks=16`), true-continuous-decode via a CHAIN of ~30-126 relay hops (`chunk_positions_stitch`/`make_batch_stitch`/`ar_decode_stitch`, all new code in `kvmem/hmn.py`).   - **New design** (current): no relay chain at all. Encode n_chunks chunks, then a SINGLE query recalling the SUFFIX of the source — warmup anchors partway through (8 ground-truth bytes), response must generate everything after that anchor through the true end, whatever length that is. New `traj_suffix` trajectory constructor (`kvmem/hmn.py`, registered in the `weave_mix` dispatch as `pattern='suffix'`) builds this as `Q(n_chunks-window_chunks, n_chunks)` — `window_chunks` here means "how many chunks back from the end the anchor sits," not a sliding window; enforced `>=2` so there's always a non-trivial response (the degenerate "warmup right at the end" case is excluded by construction). Since there's only ever one query (`op_idx=0`, always exempt from the `hops`-bounded relay restriction), none of `hops`/`forward_granularity`/`segment_checkpoint` are needed — a plain dense forward pass, and `L` is dramatically smaller (1452 at n_chunks=16 vs. 2800-4900 for the abandoned chain versions).
  - **Curriculum**: 3 stages in one run (continuing the same model/optimizer) ramping `n_chunks` up — {2,4} → {2,4,8} → {2,4,8,16} — each stage additionally mixing several `window_chunks` values so the warmup anchor lands at varying distances from the end (the practical stand-in for "warmup from any byte index," since each distinct shape needs its own fixed packed-sequence layout). Warm-started from `hmn_weave_c64`'s checkpoint (chunk_len=64-matched, see that config's own docstring).

- **`kvmem/hmn.py` promoted to the opcode+shared-value-alphabet, no-chat-tags design — STATE-role ambiguity fixed.** Without chat tags, an encode's claim-STATE and a query's own recall-STATE share the same token family — no vocab-level signal distinguishes them, only local order. Fix: one **opcode token** (`update`/`noop`/`feedback`) per STATE emission + a single **shared value alphabet** across all three roles. Separately found the query's own STATE emission is **redundant for the terminal op** (nothing relays from it) but **load-bearing for any non-terminal op** (it's the `h_t=f(h_{t-1},x_t)` transition output itself — masking can't substitute for a value that was never computed). ## 2026-09-06 to 2026-09-09 — `kvmem_jax` fork: MLP-capacity (refuted) then STATE-capacity (partial win) ablations at the chunk_len=16→32 collapse

**Context**: Experiment 2 (above) stalled hard at `chunk_len` 32/64 (stage 5/6, MEAN collapsing to
single digits). Two capacity-increasing hypotheses were tested in sequence, both on a new fork
(`kvmem_jax/`, renamed from an earlier `kvmem_mlp/` — a deliberately non-DRY, standalone copy of
`kvmem/hmn_jax.py`, not imported by or importing from the original tree).

### Hypothesis 1 — FFN/MLP capacity: REFUTED

Added real `block_type='attn_mlp'` support to `kvmem_jax/hmn_jax.py` (the original `kvmem/hmn_jax.py`
only ports `single_attn`) — `FFN`/`AttnMlpBlock` JAX port, `d_ff=256`, same `n_layers=16` attention
depth. Re-ran the full recall1024 curriculum (`hmn_tpu_recall1024_jax_incremental_mlp.py`) warm-started
from an MLP-enabled one-shot baseline (`hmn_tpu_sanity_w25_rope_jax_mlp.py`, stages 0-3 all ~80-88%,
comparable to the original non-MLP baseline).

| stage | shape | no-MLP (Experiment 2) | **MLP variant** |
|---|---|---|---|
| 0-2 | n_chunks 2/4/8, chunk_len=8 | 100/89.2/86.2% | 100/98.1/95.4% (better) |
| 3 | n_chunks=16, chunk_len=8 | 83.5% | 70.7% (worse) |
| 4 | n_chunks=16, chunk_len=16 | 61.5% | 57.4% (worse) |

### Hypothesis 2 — STATE-register capacity: PARTIAL WIN

Same fork, `block_type='single_attn'` (MLP disabled again — isolating STATE capacity as the only
variable), `state_len=8` (up from 4), `state_vocab_size=2` (up from 1). Renamed the sanity/one-shot
config lineage to `hmn_oneshotrecall_jax*.py` for this ablation.

runs exhausted may not reflect what the task actually needs once that's fixed.

### Infra saga along the way (all resolved)

1. **Silent process deaths, no trace, repeated ~5-6 times across both nodes** — root-caused, twice
   over, to two DIFFERENT bugs: (a) a stale `log_base='kvmem_mlp/logs'` string literal left over from
   renaming the fork folder `kvmem_mlp`→`kvmem_jax`, meaning every run's real, complete logs were
   quietly landing at the OLD path (`~/kvmem/kvmem_mlp/logs/...`, which still existed on both remote
   nodes) — nothing was ever actually lost, wrong path was being checked; (b) a genuine
   `RESOURCE_EXHAUSTED` HBM OOM (`Used 33.19G of 30.75G`) once `bucket_lengths=True` was introduced to
   get past a 32-distinct-shape compile wall, invisible via `tmux` (which loses the pane/stderr the
   moment the process crashes) but caught immediately once launched via `nohup ... > file 2>&1 &
   disown` instead. Fixed by adding `grad_checkpoint='block'` (all 16 layers' attention matrices were
   being retained simultaneously for backward at `Lb`~784-1168 without it) and switching all future
   launches to `nohup`+`disown` with real file redirection instead of bare `tmux`.
2. **32-distinct-shape compile wall** (stage 5 of the recall1024 redo, `n_chunks=16` × multiple anchor
   positions) — fixed via `bucket_lengths=True` (collapses 32 shapes into 4-8 padded buckets).

### URGENT, unresolved TODO — single-chip, low-MFU the whole time

**Every run in this entire ablation used only 1 of the v4-8 node's 4 chips.** Direct evidence from the
`[util:...]` log lines every run prints: `chip0: duty_cycle=100%` (busy) but
`chip1/chip2/chip3: duty_cycle=0.0%, HBM=0.00/30.75GiB` (completely idle) on every single check, on
both nodes, across every config. HBM usage on the one active chip was only ~7-9% of capacity
(2.2-2.7 GiB of 30.75 GiB). `data_parallel=True` (already implemented in `kvmem_jax/hmn_jax.py` via
`jax.jit`+`Mesh`/`NamedSharding`) was never enabled for any of these runs. Given the model is tiny
(~1.1M params) and batch sizes were 32-512 at `L`~700-1200, the matmuls are almost certainly far too
small to saturate a v4 chip's systolic array either — real MFU is likely very low even on the one chip
used, independent of the chip-count issue. **This means every wall-clock/step-count observation in
this whole ablation (how many steps stage 5/6 needed, how long each stage took) should be treated as
an artifact of a badly-underutilized setup, not a property of the task itself.** Both bucket-config
runs (2026-09-10) exhausted their full 260,000-step budget still under-single-chip and finished at
14.7-15.8% (stage 7, the final `enc_hops`-bounded shape) — well below any early-stop gate. TODO before
drawing firm conclusions about whether that final number (or the stronger 27.5-28.6% at chunk_len=32
partway through) is close to a real ceiling: retrain with `data_parallel=True` (batch size divisible
by 4) and re-measure — it's entirely possible the step budget just ran out before convergence, not
that the model hit a genuine capacity wall.
