## Quickstart — what is this, assuming you know nothing about the project

**The task**: take a byte sequence, compress it into a small fixed-size
register, then reconstruct the original bytes exactly (byte-for-byte) from
that register plus a short seed. Think of it as a learned, lossless
compression/recall system, not a language model in the usual sense — the
model never has to understand meaning, only to memorize and reproduce
bytes exactly.

**The model — a causal transformer, minus the MLP.** Every block is:

```
x = x + attn(norm(x))
```

That's it — no feedforward layer. (Standard transformers do
`x = x + attn(norm1(x)); x = x + ffn(norm2(x))` — two sublayers per block.
This project drops the FFN and doubles the layer count instead, so total
attention-op count matches a standard transformer of half the depth.) This
is `block_type='single_attn'` in `kvmem/hmn.py`, the project's default.
Standard causal self-attention otherwise: RoPE positional encoding, causal
masking (plus extra masking rules described below), multi-head attention.

**The vocabulary**: 256 raw byte values (0-255) plus a handful of special
tokens — 6 "tag" tokens that mark region boundaries (`<src>`, `</src>`,
`<query>`, `</query>`, `<response>`, `</response>`) and a small cyclic
alphabet of placeholder tokens for the compressed register (`STATE_0`,
`STATE_1`, ...). Total vocab size 274 by default. See `kvmem/hmn.py`'s
vocab-section docstring for the exact ID layout.

**The compressed register — `STATE`**: a fixed-width span of token
positions (`state_len` tokens, e.g. 8) whose *embeddings* the model fills
in with whatever it needs to reconstruct the source bytes later. The token
IDs at those positions are just placeholders (`STATE_0`, `STATE_1`, ...) —
what actually carries the information is the *learned representation* the
attention mechanism computes there, not the token identity. This is the
bottleneck the whole architecture is built around: everything the model
needs to recall must pass through this narrow register, because masking
rules (below) block direct attention back to the original raw bytes at
recall time.

## Training trajectories: E, S, Q, (R)

Every training example is built from a short sequence of "moves." Three are
real, explicit operations in the code (`E`, `S`, `Q`); the fourth
(**R**esponse) isn't a separate move — it's what a `Q` naturally produces —
but thinking of the full cycle as **E → S → Q → R** is the clearest mental
model for how one recall unit works end to end:

- **E (Encode)** — ingest one chunk's raw bytes: `<src>` + `chunk_len` raw
  bytes + `</src>`. No compression happens yet.
- **S (State)** — emit one `state_len`-wide `STATE` region right after an
  `E`. This is where compression actually happens — the model must fill
  this register with enough information to reconstruct the chunk later. An
  `S` that does NOT immediately follow an `E` is a **relay hop** instead
  (see "The relay" below) — same token shape, different role, determined
  purely by what came before it.
- **Q (Query)** — ask the model to recall a byte range: `STATE` (built
  fresh for this query) + `<query>` + a short warmup seed (a few real bytes
  from partway into the range) + `</query>` + `<response>` + the rest of
  the range, generated byte-by-byte + `</response>`.
- **R (Response)** — the byte-exact output of a `Q`. Not its own token or
  operation — it's the `<response>...</response>` content a `Q` always
  produces. Evaluation compares this against ground truth, byte-for-byte.

**Every chunk must be `E`ncoded and `S`tate-compressed before any `Q`uery
can reference it** — attention is causal, so a query literally cannot read
content that doesn't exist yet in the sequence.

**A compact DSL expresses any trajectory as a string** (`parse_traj_dsl` in
`kvmem/hmn.py`): `E4` means "ingest 4 chunks, each immediately followed by
its own `S`" (expands to `E S E S E S E S`); `Q(0,2)` means "query the byte
range spanning chunks 0-1." A few named shapes:

| Pattern | DSL | What it tests |
|---|---|---|
| `batch` | `E4 Q(0,2) Q(1,3) Q(2,4)` | encode everything, then query in schedule order (the shape every currently-trained checkpoint actually learned) |
| `stream` | `E2 Q(0,2) E S Q(1,3) E S Q(2,4)` | interleaved encode/query — query before all content exists |
| `interleave_delayed` | `E4 Q(2,4) Q(1,3) Q(0,2)` | encode everything, then query in *reversed* order |
| `repeat_query` (test-only) | `E4 Q(0,2) Q(1,3) Q(2,4) Q(0,2)` | re-query an already-answered span — tests whether the relay preserves information across multiple hops |

### Worked example: `E2 Q(0,2)`

Two chunks (`chunk_len=16`), one query spanning both (`warmup_len=8`,
`state_len=8`). This is exactly `chunk_positions_traj(chunk_len=16,
state_len=8, warmup_len=8, ops=parse_traj_dsl('E2 Q(0,2)'))`'s real output —
every position number below came from actually running it, not a
hand-drawn illustration:

```
pos    0      1..16          17     18..25     |  26     27..42         43     44..51
       <src>  16 raw bytes   </src> STATE       |  <src>  16 raw bytes   </src> STATE
       \_______ chunk 0's E _______/ \_S_/      |  \_______ chunk 1's E _______/ \_S_/

pos    52..59  60      61..68         69       70          71..94                95
       STATE   <query> 8 warmup bytes </query>  <response>  24 generated bytes   </response>
       \_ Q's own STATE _/ \_ ground-truth seed _/           \_ model's output, compared to truth _/
```

Total length 96 tokens. Concretely: `<src>` at 0, 16 raw bytes at
[1,17), `</src>` at 17, chunk 0's `STATE` at [18,26); `<src>` at 26, chunk
1's 16 raw bytes at [27,43), `</src>` at 43, chunk 1's `STATE` at [44,52);
then the query's own fresh `STATE` at [52,60), `<query>` at 60, 8 warmup
bytes at [61,69) (real ground-truth bytes, seeding the recall), `</query>`
at 69, `<response>` at 70, 24 generated bytes at [71,95) (`chunk_len*2 -
warmup_len = 32-8 = 24`, the part the model must produce from nothing but
its own `STATE` + the warmup seed), `</response>` at 95.

**Where `refine` (refine rounds, `n_refine>0`) fits in** — not a new DSL
primitive, just an optional *extra structure appended after any `Q`*: a
first attempt (`STATE`+query+response, exactly the `Q` above) followed by
one or more refinement rounds, each shaped `state` + `<response>`-wrapped
feedback + `feedback_state` + a fresh `<query>`/`<response>` pair, in that
exact positional order (verified directly against `_emit_round`'s source
and cross-checked against the archived pre-rewrite architecture, which
uses the identical ordering). `state` and `feedback_state` are the two
STATE registers a refine round builds: `state` is built first and is
functionally identical to every other STATE region (encoding STATE,
round-0 STATE); `feedback_state` is built *after* incorporating this
round's argmax feedback and is what actually seeds the fresh
`<query>`/generation — it also has its own dedicated tail-vocab
placeholder family (`HMN_FEEDBACK_STATE_FAMILY`), distinct from `state`'s
(added since no `n_refine>0` experiment has ever been trained, so there
was no checkpoint compatibility to preserve when introducing it). Extending
the example above with `n_refine=1` appends exactly this after position 95:

```
pos   96        104  105              129  130       138  139             147  148        173
      [state]   <response>[argmax feedback]</response>[feedback_state] <query>[8 bytes]</query><response>[24 bytes]</response>
```

**What "argmax feedback" actually is, precisely**: the model's own
prediction from a prior forward pass, NOT ground truth. Training runs each
packed sequence twice — pass 1 (no gradient) computes logits for the whole
sequence with round 0's response still teacher-forced from ground truth;
`_fill_argmax_fb` then takes the argmax of pass 1's logits at round 0's own
output positions and overwrites the `am0:am1` slot with THAT (the model's
own greedy guess, right or wrong); pass 2 (with gradient) then runs on this
updated sequence, and round 1's loss is computed against ground truth using
this self-generated feedback as context. This is the actual self-correction
mechanism — the model learns to fix its own mistakes, because what it sees
fed back is genuinely what it predicted, not an idealized answer.

### Why `state`/argmax-feedback/`feedback_state` don't get their own warmup

This is the part that isn't obvious on first read, so spelled out fully.
Looking at the masking rule that governs a refine round's `state`, the
argmax-feedback region, and `feedback_state` (`kvmem/hmn.py:918-925`,
"refine feedback isolation"): all three are blocked from raw chunk bytes
and from every rec_block's own raw *output* region — but **not** blocked
from encoding-pass `STATE` or from earlier rounds' `STATE`/warmup/argmax
regions. Concretely:

- **`state`** can freely attend (causally) to every encoding-block
  `STATE` — the compressed summaries built during the `E`/`S` phase. That's
  its actual job: begin re-deriving an updated representation from what's
  already been compressed, *before* it's even seen this round's own argmax
  feedback (which comes *after* it positionally — causal masking means
  `state` cannot see its own round's argmax content yet, only earlier
  rounds').
- **The argmax-feedback region** needs no warmup of its own either — it's
  not generating anything at all, it's a byte-exact *replay* of the
  previous round's own prediction, already fully determined by
  `_fill_argmax_fb` before this forward pass even starts. Its only job is
  to sit there and be visible (causally) to whatever comes after it.
- **`feedback_state`** then attends to `state` + the argmax feedback (both
  causally visible, both positioned before it) + the encoding-pass
  `STATE`s, and merges all of that into an updated compressed
  representation.

**Why the warmup/query is only needed once, right after `feedback_state`**:
warmup's specific job is narrower than "give the model context" — it's
"anchor the model to one exact byte offset within the target range, so
autoregressive generation continues from a known, unambiguous point."
`state`/argmax/`feedback_state` never generate byte output themselves —
they only build/refine the compressed representation. Only the step that's
actually about to *produce new bytes compared against ground truth* (the
response following the fresh query) needs that anchor. Everything upstream
of it is "prepare better state," not "generate," so it has no need for a
seed of its own.

### Full worked example: `n_refine=2`, every region labeled by content type

Same setup as above (`chunk_len=16`, `state_len=8`, `warmup_len=8`,
`E2 Q(0,2)`), now with two refinement rounds. Every position number below
is real output from `chunk_positions_traj(..., n_refine=2)`, not hand-drawn.
`L=252` total.

**Encoding pass** (positions 0-51, unchanged from the `n_refine=0` example
above): `<src>`+16 raw bytes+`</src>`+`STATE` for chunk 0 (0-25), same for
chunk 1 (26-51). Every byte here is real source content — nothing
teacher-forced or argmax about it, it's simply the input being compressed.

**Round 0 — initial, positions 52-95** (`STATE` + `<query>` + `<response>`):
- `STATE` [52,60) — placeholder tokens (`STATE_0`/`STATE_1`/... cycling),
  filled by attention/computation, not literal content.
- `<query>` tag at 60, warmup bytes [61,69) — **real ground-truth bytes**,
  a genuine seed sliced from the true source, always ground truth, never
  generated or predicted.
- `</query>` at 69, `<response>` at 70, output bytes [71,95) — **ground
  truth**, filled from the true source during batch construction. This is
  the LOSS TARGET for round 0: the model predicts each byte here via
  next-token prediction, and the loss compares its prediction against this
  ground truth. It is *not* teacher-forced input in the sense of "helping
  the model cheat downstream" — nothing later in the sequence is allowed to
  attend back to these bytes directly (the output bottleneck blocks that);
  it's ground truth *because it has to be, to compute a loss against it*.

**Round 1 — refine, positions 96-173** (`state` + `<response>`-wrapped
argmax feedback + `feedback_state` + `<query>` + `<response>`):
- `state` [96,104) — placeholder tokens (see the vocab-family note below).
- `<response>` at 104, argmax-feedback bytes [105,129) — **the model's own
  greedy prediction from round 0**, NOT ground truth. Mechanically: this
  training step runs the whole packed sequence through the model TWICE.
  Pass 1 (no gradient) computes logits for the full sequence, with round
  0's response still holding its ground-truth placeholder from batch
  construction. `_fill_argmax_fb` (`kvmem/hmn.py:1102`) then takes
  `argmax(pass_1_logits[round 0's own output positions])` and overwrites
  THIS region (`am0:am1` = [105,129)) with that — the model's own guess,
  right or wrong, byte for byte. Pass 2 (with gradient) then runs on this
  updated sequence. This is the literal self-correction signal: what
  round 1 "sees" here is genuinely what the model predicted, not an
  idealized answer — so round 1 has to learn to recognize and fix its own
  mistakes, not just copy a clean reference.
- `</response>` at 129, `feedback_state` [130,138) — placeholder tokens,
  from `feedback_state`'s own dedicated alphabet (see below).
- `<query>` at 138, warmup bytes [139,147) — **ground truth again**, a
  fresh seed for this round's own attempt (independently drawn per round —
  can be the same byte offset as round 0's warmup or a different one,
  depending on `warmup_x_dist`).
- `</query>` at 147, `<response>` at 148, output bytes [149,173) —
  **ground truth**, round 1's own loss target, same treatment as round 0's
  response above.

**Round 2 — refine, positions 174-251** (identical shape to round 1):
- `state` [174,182), `<response>`-wrapped argmax feedback [183,207) —
  this time **round 1's own prediction** (`argmax_src_c0=149`, pointing at
  round 1's own `c0`), fed back the same way round 0's was fed into round
  1. `feedback_state` [208,216), fresh `<query>` warmup [217,225), final
  `<response>` output [227,251) — ground truth, round 2's own loss target.

**The pattern that repeats, stated precisely**: round *k* (for *k*>0) is
`state → argmax(round k-1's own output) → feedback_state → query(ground
truth seed) → response(ground truth target)`. The argmax feedback is
*always* backward-looking by exactly one round (never two rounds back,
never the running "best" attempt — literally whatever the immediately
preceding round predicted); the response at the end of *every* round,
initial or refine alike, is *always* ground truth, never argmax — argmax
content only ever appears in the one dedicated `am0:am1` slot per refine
round, nowhere else.

**Vocab families**: encoding `STATE`, round 0's `STATE`, and a refine
round's own `state` are all filled with the exact same cyclic placeholder
token sequence (`_cyclic_state_ids`, e.g. `[STATE_0,STATE_1,STATE_0,...]`
at `state_vocab_size=2`, ids 262-263 by default) — computed once per
training batch and reused everywhere. `feedback_state`, by contrast, is
filled from its own dedicated tail-vocab family
(`_cyclic_state_ids(..., family=HMN_FEEDBACK_STATE_FAMILY)`, ids 264-265
by default) — a distinct, role-based placeholder alphabet so
`feedback_state` carries a content-level identity signal ("this register
is about to seed generation") instead of relying purely on position, added
since no `n_refine>0` experiment has ever been trained (so there was no
checkpoint compatibility to preserve when introducing the split). Both
families sit in the vocab's tail-append region and fit comfortably under
the default `V=274` (2 families × `state_vocab_size=2` = 4 of the 12 free
tail ids). Position still fully disambiguates the *roles* via the masking
rules — the vocab split is an additional signal, not a replacement for it.

**Status**: `chunk_positions_hop` supports this today (`hp['n_refine']`,
default 2 in the dispatch though every currently-trained checkpoint uses
`n_refine=0`); the `weave` DSL's builder (`chunk_positions_traj`) accepts
the same `n_refine` parameter structurally, but `weave_mix` training
hardcodes `n_refine=0` and there's no `E`/`S`/`Q` token that requests a
refine round explicitly — see the stage-status table below (`refine` is
listed "not started" for a reason: the position/mask machinery exists, but
nothing has actually been trained with it under the current
vocab/architecture).

`batch`/`stream`/`interleave_delayed` are safe to *train* on
(`stage['weave_mix']`, see below). `repeat_query` and its relatives are
**test-only** — training on them would defeat their purpose as
generalization probes, and the code actively rejects them if you try.

## The relay (`hop`) — carrying information between chunks

Within one `Q`, everything is straightforward causal attention. The
interesting part is **across separate recall units** ("chain steps" in this
project's terms) — e.g. training on `chain_steps=[(0,2),(1,3),(2,4)]` builds
three separate recall units in one packed sequence, each needing its own
`STATE`.

A strict invariant (the **nochain blackout**) blocks each chain step's
`STATE` from directly attending to *any* earlier chain step's raw content —
otherwise the model could "cheat" by reading a previous chain step's
already-decoded output directly instead of going through its own
compression. The **only** sanctioned exception is the **relay**: chain step
*i*'s `STATE` row gets a narrow, explicit attention permission to read the
last `hops` chain steps' own `STATE` columns directly (nothing else — not
their warmup, not their response, not raw chunks).

- `hops=0` (default): no relay at all — every chain step is fully
  independent.
- `hops=1`: chain step *i* can see chain step *i-1*'s `STATE` only. This is
  what every currently-trained relay checkpoint (`hop`, see below) actually
  used.
- `hops>1`: chain step *i* can see the union of the last N chain steps'
  `STATE` — implemented and verified, never yet trained to convergence.

This is a **learned** attention permission, not a forced copy — the model
decides via ordinary backprop what's worth putting in `STATE` for a future
chain step to read, rather than having a fixed rule imposed on it. (An
earlier design, `h_inject`, forced a literal feature-vector copy between
chain steps with the gradient cut off; it was deleted after this
attention-based approach was shown to substantially outperform it — see
`docs/HISTORY.md` if you want that story.)

## Validation and testing — what the numbers mean

**Val**: deterministic, rule-generated byte sequences —
`make_test_sequences` produces `up_counter` (`0x20, 0x21, 0x22, ...`
wrapping), `down_counter` (same, descending), `odd`/`even`/`linear`/
`sawtooth`/`palindrome`/`geometric` — held-out, never seen during training,
restricted to printable-ish bytes `[0x20, 0xFF]`. Cheap and fast to
evaluate, used every `eval_every` training steps. `hp['val_n_seqs']`
controls how many of these get used (commonly 3: `up_counter`,
`down_counter`, `odd`).

**Test**: a real text file (`datasets/suratalfatihah.txt` by default),
loaded via `load_chunks_padded` and split into chunks the same way training
data is. This is the "does it work on natural, non-synthetic byte content"
check, run alongside val but reported separately.

**Metrics**:
- **`match%`** — percentage of output bytes that exactly match ground
  truth, for one `Q`'s response region.
- **`span/MEAN`** — average `match%` for a given byte range across all val
  (or test) sequences.
- **`STITCHED_MEAN`** — average match% across the *entire* stitched-together
  output (all chain steps' responses concatenated) — only meaningful when
  the trained `chain_steps` schedule covers the *entire* source (true for
  multi-chain-step schedules like `hop`'s; not true for `solo`'s
  single-chain-step schedule, where it's capped at ~43% by construction
  since untested chunks are never decoded — watch `span/MEAN` there
  instead).

**Zero-shot stitching, already built into every eval**: only the *first*
chain step's warmup is seeded from ground truth. Every later chain step's
warmup comes from the model's own previously-decoded bytes — so every
reported number already reflects genuine end-to-end autoregressive
decoding, compounding whatever errors the model makes, not an idealized
teacher-forced number.

| Stage | Config | What it does | Status |
|---|---|---|---|
| `solo` | `kvmem/configs/hmn_single_recall.py` | one chain step, no relay — the bootstrap case | Done |

**The open question right now**: `hop`'s chain-memory recovery probe
(`kvmem/eval_weave.py --patterns repeat_query`) failed cleanly — a
re-queried span dropped from 100% to 0.0% after 3 relay hops. `weave_mix`
was built to test whether this was a training-exposure gap (never trained
on repeated queries) rather than a relay-mechanism failure — re-run against
`weave_mix`'s finished checkpoint, the result is a partial, non-clean
improvement (0.0-4.2% recovery instead of a uniform 0.0%), confounded by
`weave_mix` having been warm-started from `solo` rather than a strong `hop`
checkpoint (so it had to learn the relay AND generalize at once — see
CLAUDE.md's `weave_mix` entry for the full numbers). Not resolved cleanly;
a cleaner follow-up would isolate relay-strength from generalization by
warm-starting from a strong `hop` run instead.

**Structured-data generators** (`kvmem/structured_data.py`, for the
`squeeze` compression test): nine working generators spanning different
compressor-exploitable structure (Markov chains, cellular automata, run-length,
marginal-frequency skew, LZ77-style match-distance, mixed-order blends), plus
five documented-but-unbuilt placeholders for future extensions. See that
file's own docstrings for which generator suits which purpose.
